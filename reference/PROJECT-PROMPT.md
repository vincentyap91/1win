# PROJECT: 1:1 Pixel-Perfect Casino Website HTML Replication

## 1. Objective

Reference website:
https://one-vv3591.com/

Your task is to inspect and reproduce the reference website as accurately as technically and legally possible using **HTML5, CSS3 and vanilla JavaScript**.

The target is a 1:1 visual and front-end behavioral replication, not a redesign, modernization, simplification, or interpretation.

**Primary goal: Maximum achievable visual and front-end fidelity to the original website.**

Do not assume or claim 100% accuracy without verification.

## 2. Strict Design Replication Rules

Preserve the original website's:

- Layout and page structure
- Typography, font family, font weight and font sizes
- Line heights and letter spacing
- Text content, alignment and wrapping
- Colors, gradients and transparency
- Exact padding, margins, gaps and spacing
- Container widths, heights and positioning
- Border radius, border thickness and shadows
- Icons, illustrations, images and logos
- Navigation, headers, sidebars and footers
- Buttons, tabs, inputs and cards
- Hover, focus, selected, disabled and error states
- Responsive layouts and breakpoints
- Sticky elements, scrolling behavior and overlays
- Animations, transitions and interactions

**Do not redesign, optimize, simplify, or creatively reinterpret anything.**

Do not substitute a visually similar component when an exact implementation is possible.

Do not generate replacement artwork or invent missing interface elements without documenting and obtaining approval.

Use original assets and fonts only when access and usage rights permit. Report any unavailable or restricted asset.

## 3. Phase 1 — Website Investigation

Before writing code, inspect the original website using a real interactive browser.

Do not rely only on the homepage, search-engine snippets or static HTML extraction.

Investigate:

1. All publicly accessible pages and navigation routes.
2. Desktop, tablet and mobile layouts.
3. Navigation menus and submenus.
4. Dropdowns, tabs, filters and search interfaces.
5. Forms, validation messages and input states.
6. Popups, modals, tooltips and notifications.
7. Carousels, banners and promotional components.
8. Loading, empty, success and error states.
9. Guest and authenticated layouts, where authorized test access is available.
10. Different scroll positions and page sections.

Create a complete page inventory and sitemap.

For every page, document the URL, visible components, available interactions, responsive behavior and inspection status.

Never assume that two pages are identical without checking.

If a page is inaccessible, record it as a blocker instead of inventing its design.

## 4. Phase 2 — Design and Asset Extraction

Identify and document the reference website's design system.

Capture:

- Exact or sampled color values
- Typography definitions
- Spacing and sizing values
- Layout dimensions
- Responsive breakpoints
- Button specifications
- Card and container styles
- Image and icon assets
- Shadow, gradient and border values
- Component states

Use actual browser measurements and screenshots whenever possible.

Do not estimate measurements when reliable inspection is available.

Preserve the original content and asset proportions.

Avoid using screenshots as substitutes for actual page implementation.

All recreated UI must use real HTML elements, CSS and working JavaScript.

## 5. Phase 3 — HTML Implementation

Use:

- HTML5
- CSS3
- Vanilla JavaScript

Avoid unnecessary frameworks.

Organize the project into reusable components, shared styles and separate page files or routes.

Every discovered page must be represented in the implementation.

All internal navigation links must work.

All front-end interactions should behave consistently with the inspected reference.

Implement interactive elements including menus, carousels, search, filters, tabs, modal dialogs, state changes and form validation.

For functionality that requires an unavailable backend, implement clearly identified local demo behavior where appropriate.

Do not claim that simulated balances, authentication, deposits, withdrawals, wagering or game-provider integrations are real.

Never collect, store or transmit real user credentials or payment details through a replica interface.

## 6. Phase 4 — Responsive Replication

Inspect and compare at these viewport sizes:

Desktop:
- 1920 × 1080
- 1440 × 900

Tablet:
- 768 × 1024

Mobile:
- 390 × 844
- 430 × 932

Also verify layout behavior between these widths.

Do not simply shrink the desktop layout.

Match the reference's actual mobile navigation, component arrangements, card sizing, spacing and visibility rules.

Preserve the reference's responsive behavior wherever observable.

## 7. Phase 5 — Mandatory Screenshot Comparison

This is a critical requirement.

For every page and significant UI state:

1. Capture a reference screenshot.
2. Capture a local implementation screenshot.
3. Use the same viewport dimensions, browser settings and zoom level.
4. Align content, scroll position and interface state.
5. Compare the screenshots visually and, where possible, using image-difference measurements.
6. Identify mismatches.
7. Fix the mismatches.
8. Repeat the comparison.

Pay special attention to:

- Element coordinates
- Section heights
- Text wrapping
- Font metrics
- Image cropping
- Alignment
- Padding and margins
- Colors and shadows
- Responsive layout

Account for dynamic content, rotating promotions and animations when comparing screenshots.

Do not declare a page complete simply because it looks similar.

## 8. Phase 6 — Functional Verification

Test all implemented front-end interactions.

Verify navigation, links, dropdowns, buttons, tabs, search, filters, modals, forms and scrolling behavior.

Check the browser console for errors.

Check for broken images, missing fonts, horizontal overflow and incorrect mobile layouts.

Do not mark untested interactions as working.

## 9. Phase 7 — Quality Assurance Report

Maintain a detailed QA checklist covering all discovered pages and UI states.

For each item, record:

- Reference URL
- Local page or route
- Inspection status
- Implementation status
- Visual comparison status
- Functional testing status
- Known differences
- Missing assets
- Blockers and limitations

Clearly distinguish verified matches from approximate implementations.

Fix all accessible and reproducible visual mismatches before final delivery.

If an exact match is impossible, explain the specific technical, access or licensing reason.

## 10. Deliverables

Provide a complete runnable local HTML project containing:

- All implemented pages
- HTML, CSS and JavaScript source files
- Authorized local assets
- Shared component styles
- Responsive layouts
- Functional front-end interactions
- Page inventory and sitemap
- Screenshot comparison evidence
- QA report
- README with local setup instructions
- List of incomplete or simulated functionality

The project should run locally without requiring a production backend for ordinary UI navigation.

## 11. Non-Negotiable Rules

- No unsolicited redesign.
- No AI creative interpretation.
- No invented layouts for uninspected pages.
- No missing pages silently ignored.
- No screenshot-only webpage implementations.
- No arbitrary font or icon substitutions.
- No placeholders presented as final assets.
- No unsupported claims of full functionality.
- No declaration of 100% fidelity without evidence.
- No bypassing authentication or access restrictions.
- No removal of important design details merely to save development time.

Prioritize correctness and completeness over speed.

## 12. Execution Strategy

Begin with the full website audit and page inventory.

Establish a reproducible reference baseline before implementation.

Then implement the website systematically, page by page, using reusable components.

Perform screenshot comparison and functional QA after every page.

Maintain progress records so that completed work can be resumed and verified across subsequent Work sessions.

Do not stop at a homepage prototype and call the project complete.

When inspection is blocked or information is unavailable, document the issue clearly rather than guessing.

**Final standard: The closest verifiable visual and front-end behavioral replication of the reference website achievable within the available access, technology and authorized assets.**
